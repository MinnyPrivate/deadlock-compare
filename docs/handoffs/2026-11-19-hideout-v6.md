# Hideout v6 diagnosis and test handoff

November 19, 2026. The v5 runtime sample is Zachary's report that the native account field takes input and ordinary webpage clicks work, while Find does not take clicks or typing, the cursor flickers, and the page feels laggy. No v5 console capture was available with the build. The v5 handoff records a successful Find test in Chrome with the staged patch. This is a source diagnosis, with the Deadlock-specific hypotheses called out below.

## Diagnosis before changes

1. **Find field.** The v5 pak sends the live profile page `ingame=1&dlh=...` (`Builds/_build_2026-11-18_hideout_v5/source/panorama/scripts/dlhideout_test.js:4,247–271`). Its matching `website/profile.js.patch:5–66` adds the ready and input signals, page zoom, and route preservation. Fetched website main at `a41a1e9` has none of that. On those sources, the pak falls back to its four-second timeout, and the website drops the in-game query on internal routes (`profile.js:138–177`). The live response served during Zachary's test was not captured. The Find control is a native HTML `type="search"` with a normal submit listener (`profile.html:17–23`, `profile.js:170–176`). The sticky header has z-index 10 and a backdrop filter (`profile.css:57–70`). The only higher decorative layers ignore pointer events, as does the tooltip (`hero-backdrop.css:6,21–23`, `profile.css:373–376`). The v5 native strip and web body are successive rows, with a non-hit-tested wait label and a web panel above it (`hud_escape_menu.xml:92–102`, `dlhideout_test.css:29–55,102–138`, both under the v5 source folder). Valve's full-menu hit target `EscapeBackground` precedes the other panels (`hideout_test/decompiled_2026-11-16/hud_escape_menu.xml:7–10`, same folder's `hud_escape_menu.css:1`). The v5 popup is last with z-index 2000. Stock HUD ancestors also have hit testing disabled on themselves (`hideout_test/decompiled/base_hud.xml:5–6`), with no field-specific branch in those layouts. The static evidence points away from a DOM cover and blanket mouse failure. Search-widget handling, mouse-coordinate mapping at the header and Panorama-to-CEF keyboard focus remain candidates. The isolated in-game trace needs to distinguish a missed mouse event, missed DOM focus and lost keyboard input.
2. **Cursor flicker.** The page requests pointer, help, text, and crosshair cursors depending on the node (`profile.css:48–49,149–154,270–290,343–354`, plus the browser's default for inputs). At the host level v5 toggles hit testing on open/load/ready/close and treats a late web-ready after timeout as another focus request (`dlhideout_test.js:36–47,56–62,221–271`). Those transitions can cause a handoff, but no pointer-motion hit-test toggle exists in the script. v5 also registers debug mouse/activate callbacks on the web panel (`dlhideout_test.js:207–217,365–369`). The decompiled Valve ESC layout and HUD root identify the overlapping host geometry, but expose no cursor-ownership policy (`hideout_test/decompiled_2026-11-16/hud_escape_menu.xml:7–10,63–83`, `hideout_test/decompiled/base_hud.xml:5–6`). CSS cursor changes and a duplicate focus request are addressable contributors. Sustained game-versus-Windows cursor switching within a single element remains unverified and may be in the engine.
3. **Lag.** The profile always starts the full-window dust canvas. It clears and redraws on every animation frame, scales the backing store up to 2×, and animates up to 120 particles (`profile.html:14–16,35`, `dust.js:24–64,70–83`). Once themed, it also runs two rotating, breathing masks against a large heavily blurred hero image and full-screen grain (`hero-backdrop.css:6–23`). The sticky topbar uses backdrop blur, loading rows pulse, and hover can filter an entire match row (`profile.css:57–60,318–329,351–356`). The Valve menu itself uses edge world blur (`hideout_test/decompiled_2026-11-16/hud_escape_menu.css:1`), while v5 checks menu state every 250 ms and polls focus every 100 ms while open (`dlhideout_test.js:86–93,197–205,276–289`). Continuous web rendering is a concrete cost. Its share of the reported lag and the contribution of the game compositor or API latency need in-game measurement.

## v6 changes and verification

- **Find, page-side fix.** `profile.js:14–71,199–235` supports `embed=1` and recognizes the earlier `ingame=1` URL. It preserves the embed flag and sequence as you navigate profiles, uses a plain text field with an explicit focus request on mouse down, and reports mouse down, DOM focus, click, text input and submit separately. `profile.css:429–435` takes blur off the sticky bar. v6 also keeps the document at its normal CSS scale, avoiding the component-wide zoom proposed by the v5 patch. The match overlay already documents differences in its embedded browser's zoomed coordinates (`app.js:375–380`). Chromium sent all five search signals from real pointer and text events. Deadlock's own CEF input delivery remains to be tested.
- **Cursor flicker, engine fix skipped.** The embed page requests the same default cursor across controls (`profile.css:429`). In the v6 Panorama script, readiness enables and focuses the browser once, a late web-ready after timeout does not take focus again, and the web probe no longer registers mouseover or activation handlers (`source/panorama/scripts/dlhideout_test.js:222–248,323–337,368–377`). A Panorama mock verified that late ready leaves focus alone. Deadlock's cursor ownership remains a runtime question.
- **Lag, avoidable web work removed.** Embed mode skips dust initialization, hides animated rings and grain, uses a static wash in the existing hero accent, stops loading pulses, and uses a simple hover background (`dust.js:7–8`, `profile.css:429–435`). The web layout stays unzoomed. The script samples debug focus every 500 ms (`source/panorama/scripts/dlhideout_test.js:198–206`). Chromium confirmed that the effects are off in embed mode. Frame rate and API load time in Deadlock remain unmeasured.
- **Heatmap.** The scale compares each hour to the win rate in the profile header, using the active match filters and the full history behind the header. The sidebar's Last 50 or Last 200 control changes the displayed samples and keeps that baseline. The midpoint is ochre. Green marks above average, red marks below, and the background alone fades for fewer than five games. The legend and populated tooltips say "vs your X%." Chromium checked matched 55% cells, 38% versus 55%, monotonic intensity, low sample opacity, the empty hour, and a range change.
- **Website download.** The standard landing page shows **Download the app** and **Build Nov 19, 2026** beside **Find a player**. The landing page and missing-match dialog share the same ZIP path and build note. Chromium checked the landing link and that it is hidden on the embedded landing screen. The attachment and loose-executable 404 were also checked against the existing Worker with read-only requests.

All 23 Node tests passed, including the saved 20-match audit corpus and the earlier K/D reproduction. The documented loopback command served the v6 profile HTML and JavaScript on port 8766.

## In-game test

1. From the `postmortem-profile` checkout on `codex/ingame-input-heatmap`, run `python -m http.server 8766 --bind 127.0.0.1` in PowerShell. Leave it running. Open `http://127.0.0.1:8766/profile.html?embed=1` in your desktop browser and confirm that Postmortem Profile appears. This test pak uses that loopback origin to load the branch's files without a deployment. It has separate browser storage from the hosted site. The profile still uses the normal public match-data API.
2. With v6 loaded in your test setup, open the Deadlock Hideout, press ESC and click **Postmortem**. Check the popup and native controls. Expect `open`, `navigate path=profile`, a layout line, and one `focus requested target=DLHideoutWeb` unless focus is retained in a native control. `ready source=web` confirms the handshake. If the pak logs only `ready source=timeout` and the page fails to load, check whether the server saw a GET for `/profile.html`. If web-ready arrives later, expect `web ready after timeout` with no second focus request.
3. Click **Name, Steam link or account ID**, type a known player name, then click **Find**. Confirm a result or a no-results message. Repeat in a freshly opened popup with an account ID and press Enter. The signals below are recorded once per page load. No `down-search` points to a mouse delivery or hit-test problem. A mouse-down without `focus-search` points to DOM focus. Focus without `type-search` points to the keyboard path. Note whether clicking other web controls works in the same run.
4. Enter your account ID or a numeric Steam profiles link in the top-left native box. Click **Save** and confirm your profile opens. Expect `native save accepted`, `navigate path=native`, and `web native-id`. On a populated profile, scroll to **Patterns → Time of day** and hover two cells. Compare the signs and the "vs your X%" legend and tooltip.
5. At the same game resolution as v5, compare v6 with the same profile open. Hold the pointer still over the Find box, then move inside the webpage between the bar, a button and a match row. Separately cross the native strip/web boundary. Record where flicker occurs, if any. Compare short scrolls with the list already loaded and note whether typing, scrolling, or only the initial network load feels slow.
6. Click **Close**, reopen and press ESC with web focus, then repeat with native account focus. Each close should restore the Postmortem button in the ESC menu. The next ESC should resume the Hideout. Stop the local server with Ctrl+C when finished.
